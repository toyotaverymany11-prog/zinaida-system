# Исполнители видеопроизводства

Актуализация 17 ноября: реальная CPU-очистка и H100/LTX-2.5 выполнены, оба Pod удалены с подтверждением. Генерация технически прошла, геометрия объекта отклонена. Новая связка согласованного заказа и отдельной оценки сцены: [SHOTS.md](SHOTS.md). Полный набор: 123 теста; браузерная проверка новой связки использует синтетический ролик. Ранние записи ниже об отсутствии ключа и живых испытаний являются историей.

Пакет выполняет отдельные задания существующего руководителя производства: проверяет исходники, собирает видео, готовит материалы для просмотра, проверяет QR и ведёт квитанцию конкретного запуска ComfyUI. Карточки проектов, очередь, роли пользователей и публикация остаются у существующей системы.

## Установка и техническая проба

Нужен Python 3.11 или новее: закреплённый Pillow 13 не поддерживает Python 3.10. Проверено с Python 3.12, включая отдельный Linux-исполнитель с FFmpeg/ffprobe 4.4.2. Команды выполняются из корня репозитория. Создавать новые исходники поверх существующего каталога пакет откажется. На машине со старым Python используйте отдельный интерпретатор и виртуальное окружение; системный Python менять не требуется.

```bash
python3.12 -m venv production/.venv
production/.venv/bin/pip install -r production/requirements.txt
production/.venv/bin/python -m unittest discover -s production/tests -v
production/.venv/bin/python -m production.demo /tmp/production-fixture
production/.venv/bin/python -m production render /tmp/production-fixture/manifest.json --root /tmp/production-fixture --output /tmp/production-render --timeout 120
production/.venv/bin/python -m production inspect /tmp/production-render/master.mp4 --output /tmp/production-review --max-samples 8
```

Красный/синий ролик с тоном и QR является синтетической инженерной проверкой. Он не демонстрирует качество нейрогенерации, актёрскую игру, режиссуру или работу системы полного цикла.

## Описание монтажа

Полный работающий пример создаёт `production.demo`. Все медиа передаются относительными путями внутри `--root` и с обязательной SHA-256. URL, выход за каталог и ссылки через symlink наружу отвергаются. Имена и пути не вставляются в shell-команды.

Обязательные поля:

- `schema_version: 1`, `project_id`, `revision`.
- `format`: чётные `width/height`, целочисленный `fps` из поддерживаемого списка.
- `assets`: словарь `{asset_id: {path, sha256}}`.
- `clips`: ID, цель `purpose`, маршрут `route`, готовый `asset`, `duration_frames`, явное `source_audio: keep|mute`, при необходимости `source_in_seconds` и `characters`.
- `audio`: asset, role, start_frame, duration_frames, source_in_seconds и gain_db.
- `overlays`: статичный PNG, start_frame, duration_frames, x/y/width/height. Для role=qr обязателен destination.
- `characters`: версия паспорта и reference_assets. Это ссылки на утверждаемые материалы, не доказательство сохранения внешности.

Для растворения между соседними планами первый клип может содержать
`transition_after: {"type": "dissolve", "duration_frames": 24}`. Кадры перехода
перекрывают конец первого и начало следующего клипа, поэтому итоговая длина
уменьшается на этот интервал. Внутренний звук клипов смешивается линейно;
отдельная принятая звуковая дорожка сохраняет абсолютное время. Поддерживается
только этот явно заданный тип перехода; тройное перекрытие и переход после
последнего клипа отклоняются. OTIO сохраняет переход и доступные исходные кадры.

Маршруты: `existing`, `code`, `cinematic`, `character_series`, `video_recast`. Для последнего обязательны исходное видео `original_asset`, описание заменяемого героя `target` и список наших героев. Рендер начинается только с уже существующих материалов, связанных с точными хешами.

Рабочий диапазон ограничен 15 минутами, 100 планами, 64 дополнительными звуковыми дорожками и 64 PNG-слоями на задание. Рендер использует временные видео без потерь, проверяет запас диска и удаляет промежуточные файлы только после успешной сборки. Возможны большие временные файлы. Дедлайн общий для всех подпроцессов. Файл `--cancel-file` прекращает только группу процессов этого задания.

OTIO сохраняет монтажные длительности и исходники. Позиции PNG и уровни дополнительных дорожек сохранены в метаданных, а их отображение зависит от редактора. Цвет, Fusion, сложные переходы, субтитры и профессиональное сведение требуют следующего адаптера/доводки.

## ComfyUI на собственном GPU

Используется существующий `skills/creative/comfyui/scripts/run_workflow.py`. Новый адаптер задаёт для отправки `/prompt` ровно одну HTTP-попытку. Потерянный ответ и HTTP 5xx дают `outcome_unknown`; повтор команды с тем же job_id не отправляет новое задание. Квитанция записывается до POST.

```bash
production/.venv/bin/python -m production prepare-gpu workflow.api.json --job-id JOB_ID --endpoint http://127.0.0.1:8188 > plan.json
production/.venv/bin/python -m production preflight-gpu plan.json --receipts /path/to/persistent/receipts
production/.venv/bin/python -m production submit-gpu plan.json --receipts /path/to/persistent/receipts --grant grant.json --execute-authorized
production/.venv/bin/python -m production status-gpu plan.json --receipts /path/to/persistent/receipts
production/.venv/bin/python -m production download-gpu plan.json --receipts /path/to/persistent/receipts --output /path/to/new/downloads
```

`workflow.api.json` должен быть экспортирован в API-формате. Скачанный редакторский JSON с массивом `nodes` не является исполняемым API-графом. Проверка зависимостей не устанавливает узлы автоматически и не доказывает достаточность видеопамяти.

`grant.json` создаёт доверенный контроллер после разрешения расходов. Поля: `approved`, `job_id`, `endpoint`, `workflow_sha256`, `max_runtime_seconds`, `gpu_hourly_usd`, `budget_usd`. Поля связывают разрешение с конкретным планом. Секрет передаётся через `PRODUCTION_COMFY_API_KEY`, не через URL. Эта проверка является локальной проверкой заявленного бюджета; она не ограничивает счёт провайдера и не удостоверяет происхождение самого grant-файла.

Квитанции хранятся на постоянном сервере рядом с существующим состоянием задач, не на удаляемом GPU. Одно job_id означает одну попытку. Для повторной попытки после выясненного неуспеха контроллер создаёт новый ID с учётом общего лимита. Подмена графа при старом ID запрещена.

`cancel-pending-gpu` удаляет только своё ожидающее задание. Глобальный `/interrupt` не вызывается, поскольку он может остановить чужую работу. При истёкшем сроке и продолжающейся внешней работе выдаётся `requires_controller_stop: true`. До внедрения проверенного пути остановки выделенного исполнителя и отключения аренды массовый запуск недопустим.

## Проверки до принятия

Отчёт связан с manifest_sha256, output_sha256 и revision. Изменение исходника, монтажа или байтов MP4 делает старое подтверждение непригодным. Обязательны `content` и `artistic`; при героях добавляется `identity`, при замене `source_preservation`, при QR `qr`. В каждой записи нужны reviewer, evidence, category, verdict и точные хеши.

Неизвестная категория и любая переданная оценка, отличная от `pass`, блокируют
выдачу, включая дополнительную проверку. Отчёт стороннего агента с критическим
дефектом нельзя обходить положительными оценками других категорий.

## Проверки готовых основ

Скрипты `production/qualification/` проверяют изолированные установки по их
реальным интерфейсам без генерации и ключей поставщиков. OpenDirector на ревизии
`729b49bc` прошёл экспорт точной версии `.timeline.zip`, повторный импорт без
дубликатов и перезапуск. Его текущая модель таймлайна не представляет переходы;
серверный MP4 в этой пробе не реализован. Это частичный допуск редактора.
OpenMontage на ревизии `2e003e65` выполнил склейку трёх синтетических клипов и
растворения: длительность и цвета кадров проверены независимо. Проверка одного
инструмента не подтверждает качество режиссёра или готовность клиентского сервиса.

## Первичное окно заказа

`python -m production.intake --root /path/to/owner-intake --port 18117`
открывает интерфейс только на `http://127.0.0.1:18117`. Он сохраняет текст,
голосовую запись, исходное видео, изображения персонажей и отдельные условия
изменения/сохранения. Четыре явных режима: референс, лицо, тело, новый ролик.
Для замен обязательны видео и изображение персонажа. Повторный request_id
возвращает прежний заказ; изменение содержимого под тем же ID отклоняется.
Медиа привязаны по SHA-256, данные переживают перезапуск. Лимиты: 128 MiB на
файл, 2 GiB вложений, 12 файлов на группу. Изменённый файл не принимается.

Это граница приёма заказов, не новая очередь исполнителей. Автоматическую подготовку выполняет один контроллер, визуальный разбор
подключается через `--planner-codex`. Генерация и расходы не разрешаются
загрузкой заказа. HTTP-запросы ограничены
локальным Host/Origin и сессионным токеном. Публично открывать этот сервер
без отдельного проверенного входа владельца запрещено.

`python -m production.local_transcription --root /path/to/owner-intake
--order-id UUID --python /path/to/python-with-whisper --model-path /path/to/small.pt`
обрабатывает конкретную запись на CPU. Модель должна уже существовать и совпасть
с SHA-256 официальных весов small либо tiny; загрузка весов и внешние API не
используются. Запись ограничена 120 секундами, процесс по умолчанию 180 секундами.
Расшифровка появляется в окне как черновик для проверки, исходный заказ не
переписывается и производство не запускается. При настройке `--speech-python` и `--speech-model-path` контроллер вызывает
его в ходе подготовки заказа.

`python -m production.preparation --root /path/to/owner-intake --order-id UUID`
подготавливает конкретный сохранённый заказ: проверяет хеши всех исходников,
выделяет кадры с таймкодами, вероятные склейки и звук для анализа. Для голосового
заказа добавьте `--python` и `--model-path` установленного Whisper. Один общий
таймаут и `--cancel-file` действуют на извлечение и расшифровку. Без настроенной
речи независимая подготовка видео сохраняется, а блокер явно записывается.

Квитанция и подтверждённые файлы переживают перезапуск. Повтор использует только
проверенные SHA-256 материалы, повреждённые результаты пересчитывает в новом
каталоге с сохранением прежних. Параллельные попытки одного заказа исключены
блокировкой. Это вызываемый worker; intake-контроллер использует его для очереди заказов. Результат
`prepared_for_review` не означает понимание референса или художественную приёмку;
генерация и платные вызовы отсутствуют. Состояние подготовки видно в окне заказа.

Автоматическая проверка QR читает конечный MP4 в начале, середине и конце показа. Это не проверка удобства сканирования с телефона. Для видео с героями остаются отдельные просмотры движения, поворотов, перекрытий, стыков и соответствия другим эпизодам. Отсутствие такой проверки блокирует приёмку.

## Подключение к существующей системе

### Подготовка актёрских реплик

`python -m production prepare-speech speech-spec.json` готовит отдельные запросы Fish Audio, считает именно UTF-8 байты вместе с указаниями подачи и не отправляет их. Модель и голос обязательны: ошибка в имени модели у поставщика может включить платную модель по умолчанию. Пакет отвергает неизвестные модели и просроченную проверку цены. Бесплатная акция ограничена подтверждённым сроком; её продление требует новой проверки и изменения кода.

В спецификации нужны `schema_version: 1`, `model`, `quote` (model, unit=million_utf8_bytes, usd_per_unit, checked_at, valid_until, source), `voices` (provider_voice_id, version, sample_sha256) и `lines` (id, voice, spoken_text, directed_text; при необходимости temperature и speed). Квадратные скобки в directed_text задают актёрскую подачу, но произносимые слова должны совпадать с spoken_text. Пример структуры есть в `production/tests/test_speech.py`; идентификаторы там синтетические.

Изменение подачи одной реплики меняет только её ключ повторного использования. Смена модели, голоса или версии образца также меняет ключ. Принятые дорожки сохраняются отдельно; новый дубль не заменяет их автоматически. Перед приёмкой проверяются тембр, слова, ударения и игра. Расчёт цены не подтверждает наличие денег на счёте и не разрешает оплату. Исполнитель сетевых запросов и связь с существующей очередью подключаются отдельно; платного переключения здесь нет.

### Передача задания

1. Найти действующий модуль карточек/очереди и его служебную учётную запись.
2. Передавать из него неизменяемое задание, ID, ревизию, пути и пределы работы этому пакету.
3. Читать структурированный JSON-результат и сохранять ссылки в существующую карточку.
4. Подключить отдельного проверяющего к точному экспорту и полномочиям утверждения.
5. Испытать настоящую остановку внешнего рендера и аренды, восстановление после обрыва и постоянную доставку.
6. Провести художественный пилот и измерить фактическую экономику моделей.

Пакет не открывает сетевые порты, не создаёт нового руководителя, не меняет существующие службы и не публикует ролики. Его разработка не означает развёртывание на пользовательском сервере.

### Автоматическая подготовка сохранённых заказов

При запуске `python -m production.intake --root <каталог>` заказ и задание
на подготовку сохраняются в одной транзакции SQLite. Один локальный контроллер
по очереди проверяет исходники, извлекает материалы и отображает состояние
в окне. Для голосовых заказов укажите `--speech-python` и
`--speech-model-path` с уже установленным Whisper; при необходимости
`--speech-model tiny`. `--preparation-timeout` ограничивает одну попытку
(300 секунд по умолчанию).

Отменить ожидающую или выполняющуюся подготовку можно из карточки заказа.
После перезапуска прерванная попытка возобновляется один раз. Повторная
отправка того же заказа не создаёт ещё одну задачу. Старый заказ без
задания можно поставить на подготовку повторной отправкой с тем же UUID.

`awaiting_review` означает ожидание смысловой и художественной проверки.
Контроллер запускает только доступную локальную CPU-подготовку. Допуск к
генерации, вызовы провайдеров и расход бюджета отсутствуют.

### Материалы и версии плана

После подготовки ссылка «Материалы и план» открывает исходное видео,
персонажей, исходный голос, выборочные кадры, звук референса и черновую
расшифровку. Снимок доказательств проверяет хеши исходников и производных
файлов. Отдельные медиа выдаются только из записанного списка, с проверкой
хеша. Для исходного видео поддерживаются HTTP Range-запросы.

`python -m production.planning --root <каталог> --order-id <UUID>`
выдаёт проверенный пакет для анализа. `--submit plan-request.json`
сохраняет предложение плана. Те же операции доступны через локальные
`GET /api/orders/<UUID>/evidence` и `POST /api/orders/<UUID>/plan`.
Изменяющий HTTP-запрос требует существующего токена сеанса.

Запрос содержит request_id (UUID), expected_revision (0 для первой версии),
packet_sha256 и plan. В plan обязательны author, summary, scenes и
open_questions. Каждая сцена содержит source (asset_id, start, end),
observation, action, preserve, change, checks. Последние три поля содержат
списки конкретных требований. Для нового видео source может быть null.
Для замены тела/лица сцены должны покрывать полную длительность исходника
в исходном порядке. Эта проверка структуры дополняет будущую визуальную
приёмку.

Версии хранятся в SQLite. Повтор одного request_id возвращает ту же версию.
Конфликтующие правки и устаревший пакет отклоняются. Каждая новая версия
остаётся в needs_independent_review с незавершёнными смысловой и
художественной проверками. Визуальный анализатор подключается через `--planner-codex`, см. ниже.

Кнопка «Подготовить повторно» явно повторяет подготовку после исправления
причины сбоя или настройки речи. UUID повторного запроса сохраняется,
поэтому его повторная доставка не запускает ещё одну обработку.
Остановка контроллера отображается в окне. Хеширование больших файлов
учитывает таймаут и отмену.

### Качество и экономика массового производства

Основной маршрут: доступные веса моделей на арендованных GPU. Цель выбора:
минимальная полная цена принятой секунды при обязательном качестве, включая
кожу, движение, камеру и неизменность персонажа. fal и другие API не являются
автоматическим запасным маршрутом. Исключение требует отдельного решения по
качеству/полной стоимости и разрешения на расходы. При бюджете 0 Comfy executor
отклоняет генерацию, даже если в запросе указана нулевая цена GPU.

`production.generation` добавляет эти требования в проверенный пакет и план
заказа. Изменение требований меняет packet_sha256: прежний план остаётся в
истории, но требует повторной проверки. В окне видны критерии и нерешённые
условия GPU-пилота. В плане необязательное поле `cast` связывает имена героев
со списками ID их изображений из заказа. При его наличии нужны все изображения,
без повторного использования одного изображения для разных героев. Отсутствие
`cast` не означает, что герои уже закреплены; окно явно показывает это.

Каталог содержит закреплённые ревизии LTX-2.5, Wan2.2-Animate-2-14B и
Wan2.2-Animate-14B. Это проверенные метаданные, не установленные и испытанные
исполнители. Новая Animate 2 не подменяет отдельный маршрут точной замены героя
с сохранением фона. Замена только лица пока не имеет принятого исполнителя.
Наличие модели в API-каталоге не доказывает доступность её весов для установки.

`gpu_batch_cost` считает все GPU, загрузку, полезную работу, неудачные попытки,
простой, хранение, передачу и проверку. `choose_qualified_route` сравнивает
измеренные партии по одному протоколу качества и одному полному набору сцен.
Брак оплачивается, но не увеличивает принятый хронометраж. Дешёвый результат с
непринятым качеством исключается. Эти функции считают переданные измерения;
они не удостоверяют личность проверяющего и не разрешают аренду или генерацию.

Для cinematic/character_series/video_recast выдача дополнительно требует
`temporal`; для фотореалистичного профиля также `photorealism`. Для video_recast
нужна проверка `contact_and_occlusion`. `quality_profile` может быть
`photorealistic` (по умолчанию), `stylized` или `source_matched`. Стилизация не
отменяет проверки героя, движения и сохранения исходника. Все решения привязаны
к точным байтам ролика, версии монтажа и исходникам. Четыре принятых голоса Fish
не меняются.

Цены оборудования в `qualification/gpu-prices-20261117.json` являются снимком
каталога, а не прогнозом стоимости ролика. Работоспособность, скорость и качество
конкретной модели на этих GPU ещё не измерены. Нужен ограниченный GPU-пилот с
согласованным бюджетом; автоматическая аренда и загрузка больших весов отсутствуют.

### Автоматический визуальный разбор и решение по плану

`--planner-codex /path/to/codex` подключает уже авторизованный через ChatGPT
Codex CLI к тому же последовательному контроллеру. После подготовки нового
заказа контроллер создаёт черновой план. По умолчанию разбор не подключён.
`--analysis-timeout` задаёт общий предел попытки, по умолчанию 180 секунд.
Модель получает ограниченные контактные листы с таймкодами, изображения героев,
параметры видео, текст задания и черновую расшифровку голосового заказа.
Полный видеоряд и звук референса не анализируются; эти ограничения остаются
явными. До 24 приложенных изображений и 60 KB текста входа на попытку.

Исполнитель использует `--ignore-user-config`, read-only sandbox и отдельный
каталог запроса. Системные переменные с API-ключами не передаются, вход принудительно
выбран через ChatGPT; AGENTS.md, пользовательские инструкции, hooks, приложения,
оболочка и делегирование не включаются для анализа. CLI сохраняет JSON-события,
вызов инструмента или незавершённый ответ блокирует принятие предложения.
Это расход существующей квоты ChatGPT, не гарантия неограниченного бесплатного API.
Настройки общего Codex и его регистрация не меняются.

Квитанция записывается до обращения к модели. Проверенный ответ сохраняется
с хешем до транзакции плана. После сбоя завершённый ответ можно перенести в
план без нового вызова модели. Прерванное обращение без полного ответа
автоматически не повторяется. Кнопка «Повторить разбор» создаёт новый явный
запрос, повтор доставки его UUID не запускает ещё одну попытку. Отмена и
ограничение времени останавливают только процесс этой попытки. Новый план
не перезаписывает конкурентную правку владельца.

Локальные POST `/api/orders/<UUID>/analyze`, `/analysis/cancel` и `/plan-review`
требуют сессионного токена. Решение по плану содержит request_id,
expected_revision, packet_sha256, decision (`accept_plan` или `request_changes`)
и notes. Оно относится только к точной версии и материалам; новая версия его
не наследует. Это запись решения в локальном окне, не удостоверение личности
и не независимая художественная приёмка. Генерация и приёмка готового видео
остаются запрещёнными самим этим решением.

Проверка реального вызова: `production.qualification.analysis_browser_probe`.
Синтетический фрагмент модель описывает сама, результат сохраняется и показывается
в Chromium; проверяется решение по версии без разрешения генерации.
Урок интеграции CLI: после последнего `--image` нужен разделитель `--` перед
текстом. Без него CLI принимает текст за продолжение списка изображений.

### Закреплённый рецепт LTX-2.5 до платного запуска

`production.recipes.ltx25_plan` готовит API-граф T2V по официальному рецепту
Comfy Org. Он не скачивает модели и не отправляет генерацию. В `workflows/`
сохранены граф, MIT-атрибуция, исходный commit и SHA, версия ComfyUI, точные
пять файлов LTX-2.5 с ревизией, размерами и SHA-256. Вместе 39 709 872 236 байт;
это объём файлов, не оценка памяти GPU. Необязательный усилитель промпта
выключен и удалён из графа вместе с неиспользуемыми узлами. Остаётся 39 узлов,
обычный текстовый запрос, фиксированный seed и исходная пятисекундная схема.
Нативный звук модели не заменяет четыре утверждённых голоса Fish.

`verify_ltx25_weights` проверяет файлы потоково с таймаутом/отменой; совпадения
имени и размера недостаточно. Генерация требует отдельного разрешения и
положительного бюджета через существующий `comfy.Executor`. Этот рецепт
пока не доказывает качество, устойчивость лица, скорость или пригодность GPU.
Рецепты замены лица/тела и I2V не объявляются готовыми на основании T2V.

`production.qualification.comfy_cpu_probe` запускает собственный временный
ComfyUI только на loopback/CPU/offline, с отключёнными партнёрскими и внешними
узлами; браузер выгружает официальный workflow через `graphToPrompt`. Разрешена
только запись локальной настройки версии интерфейса, отправка генерации
заблокирована. После проверки процесс останавливается. Проверка нашего
исполнителя на настоящем `/object_info` выявила и исправила поддержку V3
`COMBO`, `COMFY_AUTOGROW_V3` и `COMFY_DYNAMICCOMBO_V3`.

CPU-проба 17 ноября: все 44 исходных и 39 оставшихся узлов доступны; preflight
ожидаемо заблокирован ровно пятью отсутствующими файлами моделей, очередь пуста.
Веса не скачаны. Для запуска ComfyUI в изолированном окружении понадобились
совместимые transformers/huggingface-hub/pydantic; версии в lock-файле являются
наблюдением, не полным воспроизводимым GPU-окружением. Устаревший параметр
`--disable-api-nodes` заменяет только offline: для отключения партнёрских узлов
используется именно `--disable-partner-nodes`.

### Склейка исходников по согласованному плану

В окне плана кнопка «Собрать склейку» создаёт только уменьшенный CPU-черновик
порядка и длительности исходных сцен. Это явное отдельное действие после
локального согласования плана. Описанные в плане визуальные изменения, замена
людей, генерация, озвучка Fish и художественная приёмка этим не выполняются.
Сцена без исходного видео блокирует сборку вместо подстановки случайного кадра.

Используется тот же контроллер и существующий renderer. Запрос содержит UUID,
expected_revision и packet_sha256. Повтор доставки не запускает вторую попытку.
Сборка ограничена 180 секундами, 100 сценами и 15 минутами результата; ширина
или высота до 640 пикселей. Изображение вписывается в кадр, звук исходника
сохраняется, время округляется вниз до целых кадров. Исходники неизменны.

Отмена останавливает свои подпроцессы. После сбоя готовый проверенный MP4
восстанавливается без рендера, незавершённая попытка автоматически не повторяется.
Новый запрос после сбоя явный. SHA исходников/MP4, актуальная версия и решение
проверяются перед сборкой, после неё и перед выдачей. Правка плана или отзыв
согласования блокируют старый результат. Черновик помечен source_timing_preview,
а release-check запрещает выдавать его за готовое видео даже с оценками.

API: POST /api/orders/<UUID>/preview, POST /preview/cancel; GET /preview
возвращает состояние, GET /preview/<request UUID> выдаёт проверенный MP4
с поддержкой Range. Все изменения требуют существующего сессионного токена.
Фоновый опрос страницы ограничен; производственный процесс постоянно не запущен.

Проба production.qualification.preview_browser_probe проверяет воспроизведение
в Chromium, пиксель и длительность, перезапуск, отзыв/возврат решения и мобильную
ширину. Она использует ранее согласованный синтетический заказ без новой модели.

### Подготовка весов до аренды GPU

`models-plan --root <private-models>` проверяет точные файлы LTX-2.5 без сети
и без создания каталога. `models-check-remote --root <private-models>
--hf-python <clean-hf-python>` сверяет через HEAD ревизию, размер и ETag
каждого из пяти файлов. Веса при этой проверке не загружаются.

`models-install --root <private-models> --hf-python <clean-hf-python>
--download-authorized --max-download-bytes 39709872236 --timeout 3600`
явно разрешает только установку закреплённых весов, не генерацию или аренду.
Все команды запускаются через `python -m production`; поддерживают
`--cancel-file`. По умолчанию сохраняется 1 GiB свободного диска, параметр
`--reserve-bytes` задаёт другой запас. Предварительная оценка консервативна:
частичные загрузки сохраняются, но не вычитаются из необходимого свободного
места. Предел байтов ограничивает сумму недостающих файлов, не объём
повторной передачи пакетов при сетевых сбоях и не счёт внешнего провайдера.

Используется штатный `huggingface_hub.hf_hub_download` с точным commit и
локальным каталогом. Повтор продолжает его незавершённую загрузку. Уже
установленные файлы сначала проверяются по полному SHA-256 и повторно не
скачиваются. Каждый файл появляется в каталоге ComfyUI только после проверки
размера и SHA, атомарно, без второй копии весов. Другой файл на том же пути
не заменяется автоматически. Ссылки в пути запрещены. Общий lock защищает
от двух одновременных установок. Дедлайн, cancel-file и SIGTERM останавливают
свою группу процесса загрузки. Квитанция и частичные данные остаются для
явного повтора; автоматического бесконечного перезапуска нет.

Для загрузчика есть отдельный `runtime/hf-download-linux-py313.lock.txt`.
Создайте обычный venv без `--system-site-packages`, установите lock через
`pip install --require-hashes -r <lock>` и выполните `pip check`. Lock проверен
на Linux x86_64/Python 3.13; другую платформу нужно разрешить отдельно.
Используется уже сохранённый вход HF; токены не передаются аргументами и не
записываются в квитанции. Ошибки дочернего загрузчика не выводят заголовки
авторизации и подписанные ссылки. Xet отключён для предсказуемого локального
кеша и штатного HTTP-продолжения загрузки.

`qualification.model_install_probe` проверяет настоящий путь скачивания на
маленьком README закреплённой версии LTX, независимую сверку Git blob,
повтор без нового запроса и отклонение повреждённых байтов. Это не проверка
скорости загрузки 40 GB и не испытание генерации.

Чистое CPU-окружение ComfyUI воспроизводится из
`runtime/comfy-cpu-linux-py313.lock.txt` тем же `pip --require-hashes`.
84 пакета закреплены вместе с CPU-сборкой torch 2.15.0, без наследования
системных библиотек. `qualification.comfy_clean_probe` проверяет commit
ComfyUI, отсутствие наследования, `pip check`, реальную CPU-операцию torch,
39 узлов рецепта через HTTP API и пустую очередь. Только пять отсутствующих
весов блокируют рецепт. Временный процесс останавливается; служебные данные
размещаются в отдельном каталоге. Эта сборка не подходит для генерации на
CUDA: GPU-окружение и его производительность нужно квалифицировать отдельно.

### Завершение будущей аренды

`production.rental` не создаёт и не арендует ресурсы. Он принимает доверенную
локальную квитанцию создания отдельного пилотного Pod, содержащую точные id,
уникальное имя zina-video-<32 hex> и createdAt, согласованный положительный
бюджет, полный часовой тариф, фиксированные расходы, крайний срок и запас
времени очистки. Оценка обязана помещаться в бюджет с этим запасом. Общие
ресурсы и cluster-поды не допускаются. `enforce` требует отдельный явный
execute_authorized; до дедлайна без отмены возвращает waiting без сети.

По дедлайну адаптер Runpod REST v2 сначала читает ресурс и проверяет привязку,
записывает намерение, отправляет DELETE и перечитывает результат. Только 404
при повторном GET означает terminated_confirmed. Потерянный ответ DELETE
сверяется с состоянием; неуспех ограничен пятью попытками и общим Runtime.
При неизвестном исходе сохраняется cleanup_unconfirmed, без ложного успеха.
Чужие Pod и отдельные volumes не удаляются. Вызов выполняется под блокировкой
аренды существующего доверенного контроллера; это не новая очередь.

В актуальном публичном контракте Runpod v2 нет terminateAfter/stopAfter.
Официальный CLI удалил --stop-after/--terminate-after в 2.12.0: старые флаги
не исполнялись сервером. Источник: https://github.com/runpod/runpodctl/releases
и https://api.runpod.io/v2/openapi.json (проверено 17.11.2026). Не копировать
эти старые флаги из устаревших инструкций. Требование отдельно проверенного
завершения аренды теперь видно в готовности заказа.

Граница проверки: тесты контроля используют имитацию API; реальной аренды
и удаления не было. Независимый постоянно контролируемый процесс с доступом
к Runpod ещё не подключён. На основном сервере при проверке отсутствовали
runpodctl, ключ в окружении и стандартный файл настройки; это не отменяет
доступ плагина в чате. Ключи не читались и не запрашивались. До настройки и
живой проверки такого контроля автономная аренда запрещена. Отказ сети или
самого сервера не превращается в гарантированный жёсткий предел счета.


### Независимый контроль аренды и изучение Runpod

`python -m production.rental_guard launch --lease LEASE.json --root STATE --credential-file PRIVATE_KEY --supervisor systemd` запускает только новую временную службу для уже созданного собственного ресурса. Операции создания или генерации отсутствуют. Нужен положительный согласованный бюджет в доверенном lease, точные id/name/createdAt и явное разрешение удаления. `status` проверяет heartbeat и PID; факт запуска не означает готовность.

На сервере с systemd перезапуск после SIGKILL сохраняет исходный deadline. Число перезапусков ограничено. Отказ хоста или сети не покрывается, реальный Runpod ещё не квалифицирован. Режим loopback simulation никогда не возвращает production-ready. При повреждении файла аренды очистка использует исходную проверенную запись.

Проверка без Runpod и без расходов:
`python -m production.qualification.rental_supervisor_probe --output PRIVATE_PROBE_DIR`
Она временно создаёт собственную systemd-службу, принудительно завершает её процесс, проверяет перезапуск, DELETE/GET404 на локальном HTTP и остановку службы. Выполнять только на Linux с systemd и правом создания своей временной службы.

Для владельца в собственном SSH-терминале: `python -m production.configure_runpod --credential-file PRIVATE_DIRECTORY/runpod.key`. Ключ вводится скрыто, проверяется GET списка Pods, существующий файл не перезаписывается. Секрет не передавать в чат. Проверка чтения не доказывает права удаления; это отдельный шаг живого пилота.

Процедуры, реальные ограничения и реестр 110 материалов: [Runpod operations](docs/runpod-operations.md), [source ledger](docs/runpod-sources.json). Обновлять важные контракты перед действием. Прочитанная инструкция не равна прошедшему CUDA/художественному испытанию.
